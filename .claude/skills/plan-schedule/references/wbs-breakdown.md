# WBS分解・日程算出ガイド

`plan-schedule` Skillが `schedule.md` §3（WBS）を組み立てる際の判断基準をまとめる。

## 1. `overview.md` §4 → Epic化条件

`overview.md` §4「対応範囲・役割分担」の13作業項目を、実施者列に応じて以下のように扱う：

| 実施者 | 扱い |
| --- | --- |
| Sun* | Epic化する（Sun*側の工数・日程を算出） |
| 共同 | Epic化する（Sun*側が担当する範囲のみ工数・日程を算出し、説明列にクライアント側の分担を注記） |
| クライアント | Epic化しない。隣接するSun* Epicの依存関係列に「〇〇の開始/完了はクライアント側日程に依存」と注記する |
| 空欄（未確定） | ヒアリングして確定してから上記いずれかに振り分ける（`overview.md` に書き戻す） |

**Epic ID対応（デフォルトの並び順、実施者に応じて該当行のみ生成）**:

| Epic | 対応する `overview.md` §4 の作業項目 |
| --- | --- |
| E-01 | 要件定義（要件確定・仕様化） |
| E-02 | 基本設計・詳細設計 |
| E-03 | 開発・実装 |
| E-04 | 単体テスト（UT） |
| E-05 | 結合テスト（IT） |
| E-06 | システムテスト（ST） |
| E-07 | 受入テスト（UAT） |
| E-08 | ドキュメント作成（設計書・マニュアル等） |
| E-09 | データ移行 |
| E-10 | 本番環境構築（インフラ・サーバー設定） |
| E-11 | 本番リリース作業 |
| E-12 | リリース後の運用・保守 |
| E-13 | 障害対応（本番） |

案件特性で `overview.md` §4 に行が追加・削除されている場合は、それに合わせてEpic ID・並び順を調整する。

## 2. Story粒度の自動判定（`function-list.md` 連携）

対象Epic：E-01（要件定義）／E-02（設計）／E-03（開発・実装）／E-04（UT）。

- **機能数が目安15件以下** → 1機能 = 1Story（`function-list.md` のID順にStory化）
- **機能数が16件以上** → 優先度・対象ロール・業務フローの関連性で機能をグルーピングし、1グループ = 1Story とする。グルーピング結果はユーザーに一言確認する
- 生成したStory IDは `function-list.md` の「関連WBS ID」列に書き戻す。1グループに複数機能が属する場合は、それら全機能の行に同じStory IDを記載する

E-05〜E-13（IT/ST/UAT/ドキュメント作成/データ移行/本番環境構築/本番リリース/運用保守/障害対応）は機能単位ではなく工程単位のStoryとする（例：E-05は「結合テスト実施」「結合テスト結果報告」等）。`function-list.md` の「関連WBS ID」列への書き戻しは行わない。

## 3. デフォルトの依存関係ルール

ウォーターフォール（`overview.md` §3「進め方」がアジャイル以外、または未確定）の場合：

| Epic | デフォルトの依存関係 |
| --- | --- |
| E-01 要件定義 | 依存なし（キックオフマイルストーンを起点に開始） |
| E-02 設計 | E-01完了に依存 |
| E-03 開発・実装 | E-02完了に依存（Story単位で対応する設計Storyの完了後に着手可） |
| E-04 UT | 対応するE-03 Storyの完了に依存（Story単位でペア） |
| E-05 IT | E-04の全Story完了に依存 |
| E-06 ST | E-05完了に依存 |
| E-07 UAT | E-06完了 ＋ クライアント側スケジュールに依存（Block Dでリードタイムを確認） |
| E-08 ドキュメント作成 | E-03・E-04と並行実施可。E-11（本番リリース）開始前に完了が必要 |
| E-09 データ移行 | E-02完了（データ移行方式の設計確定）後に着手可。E-11開始前に完了が必要 |
| E-10 本番環境構築 | E-01完了後、E-03と並行して着手可。E-11開始前に完了が必要 |
| E-11 本番リリース作業 | E-07合格 ＋ E-09完了 ＋ E-10完了に依存 |
| E-12 運用・保守 | E-11完了（リリース日）を開始日とし、契約期間終了日（`overview.md` §1）を終了日とする。契約期間が未確定の場合は終了日を空欄とし「契約期間確定後に反映」と注記する |
| E-13 障害対応（本番） | E-12と同期間（開始日・終了日ともE-12と同じ） |

アジャイル（`overview.md` §3「進め方」がアジャイル）の場合：

- E-01〜E-04は厳密な直列フェーズにせず、機能（Story）単位でスプリントに割り当て、スプリント内で要件確定→設計→開発→UTを並行させる
- E-05〜E-07（IT/ST/UAT）は複数スプリントの成果をまとめて実施するタイミング（例：リリース前の集中スプリント）に配置する
- E-08〜E-13は上記ウォーターフォールと同じ考え方でよい

## 4. 日程算出の考え方

各Epic/StoryについてSun*側の必要工数（人日、Block Bで確定）が決まったら、以下で開始日・終了日（予定）を算出する：

1. 依存関係ルール（本ドキュメント §3）から、着手可能な最早日（先行Epic/Storyの終了日、またはマイルストーン日）を決める
2. その時点でアサイン可能なメンバー（`stakeholders.md` §2「アサイン工数（稼働）」、`overview.md` §1契約形態に応じた単位）の稼働キャパシティを合算する
   - **ラボ型/SES（人日/月）**: 必要工数（人日） ÷ （アサインメンバーの人日/月の合計） × 30日 ≒ 所要期間（日）
   - **請負（PJ全体の総アサイン人日）**: 必要工数（人日） ÷ （アサインメンバーの総アサイン人日をプロジェクト期間で均した1ヶ月あたりの人日） × 30日 ≒ 所要期間（日）。プロジェクト期間が未確定の場合は総アサイン人日と必要工数の比率のみで前後のEpicとの相対期間を出し、絶対日付はマイルストーン確定後に調整する
3. 算出した所要期間を最早着手日に加算し、終了日（予定）とする。土日・祝日等の営業日調整は簡易的に「1週=5営業日」で見積もり、厳密なカレンダー計算はしない
4. 算出結果がマイルストーンの固定日（Block Aで「日付確定」としたもの）を超える場合は、その旨をユーザーに提示し、キャパシティ追加・スコープ調整・マイルストーン見直しのいずれかを確認する（無断で調整しない）
