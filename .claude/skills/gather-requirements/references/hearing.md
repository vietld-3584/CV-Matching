# ヒアリング詳細（Block A〜E）

各ブロックの **問いかけ方の例**、**回答の解釈ルール**、**記入順序の依存関係** をまとめる。Skillはここを参照して、ブロック内は1質問1ターンで会話を進める。

## 共通ルール

- 番号選択ではなく **キーワードで例示** する
- 自由記述の回答を許容する（曖昧な場合は確認質問を返す）
- 提案書・プロジェクト概要から推測できた項目は「〇〇と理解しましたが合っていますか？」の形で聞く（開いた質問にしない）
- ブロックの順序（A→B→C→D→E）には依存関係がある：B（機能）はA（ロール）のROLE-IDを参照し、C（業務フロー）はB（機能）の必須機能を参照し、E（用語集）はA〜Dで出てきた語を集約する。Dは他ブロックと独立して進めてよい。

## Block A: ロール一覧（→ role-list.md §1）

**問いかけ例（文書から何も取れなかった場合）**:
> このシステムを利用する人・役割を教えてください。一般利用者だけでなく、管理者・運用担当・外部連携先アカウントなども含めて構いません。

**確認質問の例（文書から推測できた場合）**:
> プロジェクト概要から、一般会員とサイト管理者の2ロールがありそうだと理解しましたが、この認識で合っていますか？他に見落としているロールはありますか？

**深掘りする項目**（1ロールずつでなく、まとめて聞いてよい）:
> 各ロールについて、想定人数・規模（例：一般会員は数千人規模、管理者は社内5名程度）や特記事項があれば教えてください。

**回答の解釈ルール**:
- 「エンドユーザー」のような曖昧な括りしか出てこない場合、権限が異なるサブロール（無料会員／有料会員等）に分かれる可能性を1問だけ確認する
- ロールIDは `ROLE-001` から連番。既存テンプレートの `ROLE-001`/`ROLE-002` は例示なので実データで上書きする

## Block B: 機能一覧（→ function-list.md）

**前提**: Block Aで確定したROLE-IDを使う。

**問いかけ例**:
> このシステムで提供する機能を教えてください。まずは思いつく範囲で構いません。あとから優先度を一緒に整理します。

**優先度の確認**:
> 〇〇機能は必須（MVPに絶対必要）・推奨・任意・対象外のどれに近いですか？

**対象ロールの確認**:
> 〇〇機能は、先ほどのロールのうちどれが使いますか？（複数ロール可）

**回答の解釈ルール**:
- 機能が多岐にわたる場合、いきなり全部を深掘りせず、まず機能名と概要を一通りリストアップしてから優先度・対象ロールを1機能ずつ確認する
- 「詳細ドキュメント」列（機能ごとの業務フロー・入出力）はこのSkillの対象外。ヒアリング中にユーザーが詳細（入出力項目や業務ルール）を話し始めても、概要レベルで受け止め、「詳細は機能ごとの仕様作成時に深掘りします」と伝えて先に進める
- 機能IDは `F-001` から連番

## Block C: 業務フロー概要（→ business-flow.md）

**前提**: Block Bで「必須」とした機能が確定していること。

**進め方**: ユーザーへの開いた質問ではなく、**AIがまずドラフトを提示**する。

**ドラフト提示の例**:
> 必須機能を中心に、主要な業務フローを次のように整理しました（mermaid図を提示）。利用者が〇〇して→〇〇して→完了、という流れで合っていますか？抜けている分岐や、管理者側の別フローがあれば教えてください。

**回答の解釈ルール**:
- 利用者フローと管理者フロー等、明らかに主体が異なる複数フローがある場合は見出しを分けて提案する
- 機能内部の代替・例外フロー（エラー時の挙動等）は描かない。ユーザーがその粒度で話し始めたら「その粒度は機能ごとの仕様で扱います」と伝えて概要レベルに戻す

## Block D: 非機能要件（→ non-function-list.md）

**前提**: `references/nfr-catalog.md` を参照。他ブロックと独立して進められる。

**問いかけ例（まず聞く）**:
> 性能・可用性・セキュリティなどで、決まっている数値目標や基準はありますか？（例：応答速度、稼働率、想定同時アクセス数など）

**ユーザーが出せない場合**:
`references/nfr-catalog.md` の該当カテゴリを参照し、プロジェクト特性（対象プラットフォーム、扱うデータの機密性、想定規模）から根拠を示してドラフトを提案する。

**ドラフト提示の例**:
> 具体的な基準がまだない場合、Webサービスでメールアドレス等の個人情報を扱う想定であることから、「セキュリティ：通信のTLS化必須」「法令・規制：個人情報保護法に基づく取扱い」あたりをドラフトとして置いておくのはどうでしょうか？後で調整可能です。

**回答の解釈ルール**:
- 「ドラフト（要確認）」である旨を必ず伝え、ユーザーの承認を得てから確定値として書き込む
- 該当しないカテゴリ（例：規制対象外の社内ツール）は無理に埋めず対象外とする
- 8カテゴリ全てを機械的に聞くのではなく、プロジェクト特性上重要度が高いものから優先的に扱う

## Block E: 用語集（→ glossary.md）

**前提**: Block A〜Dのヒアリング中に出てきた業務用語・略語・クライアント固有語をメモしておく（別ファイルに書き出す必要はなく、会話の中で覚えておく）。

**まとめて確認する例**:
> ここまでのヒアリングで「〇〇」「△△」といった用語が出てきましたが、簡単に定義を教えていただけますか？他に、社内やクライアント側でよく使う略語・独自用語があれば合わせて教えてください。

**回答の解釈ルール**:
- 一般的なIT用語（ログイン、CSV等）は基本的に対象外。業務固有・クライアント固有の語に絞る
- 定義が曖昧な場合、1問だけ確認質問を返す。決まらない場合は用語だけ記載し定義は空欄でよい（完了サマリで未確定として報告）
