# plan-project Skill

プロジェクト立ち上げ時の初期計画ドキュメントを作成するSkill。`jp-project-manager` エージェントの `PLAN` メニューから呼ばれる。

## 目的

以下の **3ファイルのみ** を記入する：

- [`docs/01_management/overview.md`](../../../docs/01_management/overview.md) — 契約・体制・進め方・制約
- [`docs/02_requirements/project-overview.md`](../../../docs/02_requirements/project-overview.md) — サービス概要・背景課題・目的
- [`docs/01_management/stakeholders.md`](../../../docs/01_management/stakeholders.md) — 体制・承認フロー・エスカレーション

**重要**：[`docs/01_management/define-of-done.md`](../../../docs/01_management/define-of-done.md) には触れない。完了の定義は要件定義書（`gather-requirements`/REQ 実行後）を前提とする別Skill（`define-of-done`/DOD）の担当であり、要件が確定する前に書いたDoDは `function-list.md` と紐付けられず中途半端になるため、PLAN段階では対象外とする。

## 参照ドキュメント

実行時に必要に応じて読み込む：

- `references/field-mapping.md` — 各入力（提案書／プロジェクト概要／見積書／コストシート）が3ファイルのどのセクション・セルに対応するか、および「文書からは絶対に取れず必ずヒアリングが必要な項目」の一覧
- `references/hearing.md` — ヒアリングBlock A〜Fの問いかけ例・回答の解釈ルール

## 入力の受け取り方

ユーザーは 提案書／プロジェクト概要（クライアント提供のブリーフ。出力ファイルの `project-overview.md` とは別物）／見積書／コストシート を、以下いずれの形でも渡せる：

1. **実ファイルのパス** — `Read` で読む
2. **チャット内への直接貼り付け**（テキスト／Markdown）
3. **何も渡さない** — その項目は最初からヒアリング対象とする

**既知の制約**：`Read` は PDF はそのまま読めるが、`.docx`/`.xlsx`/`.doc`/`.xls` はバイナリ形式のためそのままでは読めない。これらのパスを渡された場合、またはReadが失敗した場合は、確認を挟まず次の順で対応してよい：

1. **Bash経由で使い捨てのPythonスクリプトを書いて解析する**：`.docx`/`.xlsx`はZIP+XML構造なので、`python-docx`/`openpyxl`が使えるならそれを使い、無ければ標準ライブラリの`zipfile`＋`xml.etree.ElementTree`で`word/document.xml`（docx）や`xl/sharedStrings.xml`・`xl/worksheets/sheetN.xml`（xlsx）を直接パースしてテキストを取り出す。抽出したテキストはその場で読み取って使い、スクリプトや中間ファイルはプロジェクト配下に残さない（一時ファイルが必要ならOSの一時ディレクトリを使う）。
2. `.doc`/`.xls`（旧バイナリ形式）で1の方法が使えない場合、`python3`が使えない場合、または抽出結果が文字化け・空など使い物にならない場合は、それ以上手段を変えて粘らず、次のように伝える：

> 「このファイルは自動では正しく読み取れませんでした。該当部分をテキストとして貼り付けていただくか、PDF/テキスト形式で書き出して再度パスを教えてください。」

## 会話ガイドライン

- **常に「文書からの推測」を先に試し、ヒアリングは不足分のみ**に絞る。推測できた項目も「〇〇と理解しましたが合っていますか？」と確認してから確定する。
- ヒアリングは `references/hearing.md` のBlock A〜Eの単位で進め、**1ブロック内は1質問1ターン**。番号選択ではなくキーワードで例示し、自然言語の回答を許容する。曖昧なら確認質問を返す。
- D/C/Q/Sトレードオフ配分（14pt）とKPI数値は **必ずユーザーに確定させる**。提案書のトーンから仮の配分を提案してよいが、無断で確定してはならない。
- 入力が一部しかない場合もブロックしない。「見積書とコストシートが未提供のようです。体制情報などは会話で伺います」のように不足分を一言伝えた上で、ヒアリングで埋めて進める。4つとも未提供かつ他に情報がない場合のみ、5ブロックを一気に始める前に「提案書などの資料はありますか？なければ、質問しながら一緒に整理していきます」と最初に1問だけ確認する。

## メインフロー

### Step 1: 入力の確認

ユーザーから渡された 提案書／プロジェクト概要／見積書／コストシート を確認する。ファイルパスなら `Read`、テキスト貼付けならそのまま内容として扱う。読めない形式は上記のルールに従う。どれが欠けているかを把握する。

### Step 2: 既存3ファイルの確認

`overview.md` / `project-overview.md` / `stakeholders.md` を `Read` する。各セクション・セルを次のいずれかに分類する：

- **未記入**（HTMLコメントのガイドのみ、または空セル）→ 自由に記入してよい
- **記入済み**（実際の値が入っている）→ 無断で上書きしない。既存値を提示し、更新するか確認する

3ファイルとも既に完全に記入済みの場合は、その旨を伝えて「更新したい項目はありますか？」と聞き、該当項目のみ対応する（この場合、以降のStepは全項目走査ではなくピンポイント対応に切り替える）。

### Step 3: 文書からの抽出

`references/field-mapping.md` に従い、Step 1で得た入力から推測できる項目を埋める。推測した値は次のStep 4で確認を取る対象としてリストアップしておく（この時点ではまだファイルに書き込まない）。

### Step 4: ヒアリング（Block A〜F）

`references/hearing.md` を参照し、Block A→B→C→D→E→Fの順に進める。Block D（対応範囲・役割分担）は、Block A で確定した契約形態（請負／準委任）と矛盾しないかを必ず突き合わせる。特にUAT・本番インフラ構築・データ移行はクライアント側が担当するケースが多いため、思い込みで「Sun*」と確定しない。各ブロックについて：

- Step 3で推測できた項目 → 確認質問（「〜と理解しましたが合っていますか？」）
- 推測できなかった項目 → 開いた質問でヒアリング

回答が確定するたびに、その場でStep 5（ファイル反映）に進めてよい（ブロック単位で確定→反映を繰り返す）。

### Step 5: ファイルへの反映

確定した内容を `Edit` で該当ファイルの該当セルに書き込む。書き込んだ内容が実質的な変更である場合、そのファイル自身の「改訂履歴」表に日付・更新者（`plan-project skill` または対話中のペルソナ名）・内容を1行追加する（3ファイル共有の履歴ではなく、ファイルごとに追記）。

`stakeholders.md` の連絡・コミュニケーション手段と `overview.md` の進め方（コミュニケーション手段／チケット管理ツール）は同じ回答を両方に反映する（2度聞かない）。

### Step 6: 完了サマリ

3ファイルそれぞれについて、記入した内容の要約と、まだ空欄のまま残っている項目（ユーザーが回答を保留した等）を明示する。後続のSkill（`plan-schedule`/SCH、`define-of-done`/DOD等）が着手する前に把握しておくべき未確定事項として伝える。

## エラー時の対応

- 読めないファイル形式 → 上記「入力の受け取り方」のフォールバック文言で案内する
- 複数の入力文書間で内容が矛盾する（例：提案書と見積書で契約期間が異なる）→ 両方の記載を提示し、ユーザーに確定してもらう。どちらかを勝手に採用しない
- 既存ファイルの実データを上書きしそうな場面 → 必ず確認を取ってから実行する
